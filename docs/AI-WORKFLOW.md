# Регламент работы и передачи контекста DCA800

## Начало каждого сеанса
1. Открыть репозиторий smoc1983-web/Dca, проверить main, HEAD, последние коммиты. Не полагаться на память чата вместо Git.
2. Прочитать AGENTS.md, docs/AI-WORKFLOW.md, docs/JOURNAL.md (актуальная карточка и последние записи), docs/ROADMAP.md, docs/STRATEGY.md, docs/OPERATIONS.md, docs/LIMITATIONS.md, docs/VALIDATION.md. При работе в другой ветке сверить её HEAD и журнал с main.
3. Восстановить последнюю подтверждённую версию, согласованные требования, текущий этап, результаты тестов, блокеры и следующий шаг. При расхождениях сверять файлы и коммиты; не выдумывать результаты.
4. Продолжать последнее явное поручение, не считать предложение разрешением на работу. Не просить повторить уже записанные сведения.
5. Короткая команда владельца «Ок» / «ок» в контексте разработки DCA800 означает явное поручение продолжить следующий согласованный шаг, без повторного запроса подтверждения. Не отменяет остановку, отдельные запреты и требование отдельного разрешения на production.

## Журнал
docs/JOURNAL.md — каноническая хронология и инструкция передачи контекста. Сверху обновлять карточку состояния, новые датированные записи добавлять в конец; историю не стирать, исправления отмечать отдельно. Записывать каждое существенное поручение, согласование, изменение, результат теста (включая ошибку), релиз, откат, подтверждение владельца, блокер, следующий шаг. Обновлять при достижении каждого этапа и перед завершением сеанса. Не записывать секреты, реальные балансы/позиции, личную переписку или дампы: репозиторий публичный.

Шаблон записи:
- Дата, ID DCA-YYYYMMDD-NN, название.
- Поручение и статус: предложено / согласовано / в работе / реализовано / тест пройден / тест не пройден / заблокировано / отменено.
- Ветка, исходный HEAD, изменённые файлы, параметры до/после, причина.
- Тесты: команды, результаты, ссылки на CI; явно указать непройденные или непроведённые проверки.
- Production: не изменён / отдельно разрешённое изменение с проверкой.
- Блокеры, риски, следующий шаг.
SHA коммита самой записи доступен в Git после сохранения; не выдумывать его заранее.

## Порядок работы
- Сначала минимальный план и проверка актуального HEAD. Код и конфигурацию готовить в отдельной ветке; документационные записи допустимы в main. Не перезаписывать чужие изменения; при конфликте перечитать HEAD и объединить записи.
- Каждый этап включает код, целевые тесты и соответствующую документацию. Node.js >=22: npm run check и npm test либо прямые эквиваленты. Не запускать архивных отправителей. Отдельно фиксировать офлайн, CI, тестовую среду и production; успех одного не означает успех другого.
- Обновлять ROADMAP, JOURNAL и при необходимости STRATEGY, OPERATIONS, LIMITATIONS, VALIDATION. Сохранять журнал с кодом в том же коммите, где возможно; статус отдельной ветки фиксировать также в main без неразрешённого слияния кода.
- Проверить доступность записи в Git. Перед ответом сообщить выполненное, проверки, незавершённое, следующий шаг. Если нет доступа на запись, не утверждать обратное.
- Согласованные направления не равны разрешению на реализацию или деплой: соблюдать последний явный объём поручения. Не менять Worker, D1, cron, режим доставки, не сбрасывать модели, не запускать второго отправителя, не посылать тестовые Telegram-сообщения без отдельного разрешения и проверки текущего состояния. Реальные сделки размещает владелец вручную; исполнитель ордеров не входит в утверждённый план.
- Исторические модели, ручные сделки и фактический баланс различать. Историческая доходность не гарантирует будущую.
