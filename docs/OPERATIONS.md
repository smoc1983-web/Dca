# Архитектура и сопровождение

## Поток данных
Binance OHLC → runtime.fetchBars (закрытые свечи и проверка разрывов) → advance/stepEntry → обновление модели и outbox в D1 → Telegram sendMessage.

- worker.mjs: scheduled/tick, публичные источники Binance, обработка очереди и контроль режима.
- runtime.mjs: догрузка истории, нестандартные интервалы, продвижение модели.
- watchlist-engine.mjs: RSI/EMA, сделки модели, формат сообщений.
- daily.mjs: компактная ежедневная сводка.
- schema.sql: control, models, alerts, runs.

Модель хранит последний обработанный бар, RSI/EMA, cash, qty, average, номер DCA и состояние цикла. После перерыва догружаются пропущенные свечи, включая прошлые START и DCA. Нельзя сбрасывать модель в пустую позицию только потому, что реальных сделок у пользователя нет.

За tick выбирается до 10 моделей; одна модель догоняет ограниченную порцию истории. Вставка событий и обновление состояния идут batch с проверкой rev и control.epoch. ID события содержит пару, ТФ, время и тип; INSERT OR IGNORE защищает от повторной постановки.

## Доставка
Режим shadow сохраняет сигналы без обычной отправки; live доставляет pending. До двух сообщений за проход. Перед отправкой статус меняется на sending. Полученный message_id даёт delivered. Явный отказ Telegram возвращает событие в очередь с задержкой. Неясный исход становится uncertain: автоматический повтор мог бы создать дубль. Это компромисс, а не гарантия exactly-once. Зависший sending после аварийного завершения тоже требует проверки.

Задержавшийся обычный сигнал более чем на три минуты получает отметку «Пропущенный сигнал», время в Europe/Astrakhan и исходный текст. При сбое рыночных данных уже накопленная очередь live всё равно может доставляться. HTTP 451/явные региональные ограничения не обходятся.

## Сводка
При DAILY_SUMMARY=on один идентификатор DAILY:YYYY-MM-DD ставится в очередь после 06:00 UTC+4, на первом доступном tick. Включает все модели, группы по DCA, ожидающие пары, числа событий за 24 часа и отставание свечей. Время фактической доставки зависит от cron, очереди и доступности сервисов. FIRST_SUMMARY_DAY позволяет разовую первую сводку раньше 06:00; перед production проверить отсутствие устаревшего исключения.

## Продолжение на другом устройстве
Клонировать репозиторий, прочитать README/AGENTS и выполнить офлайн-проверки. Для анализа кода секреты не нужны. Для администрирования отдельно подключить существующий Cloudflare аккаунт, Worker и D1 через защищённые средства окружения. BOT_TOKEN и CHAT_ID хранить в секретах, не в git.

Перед разрешённым изменением production сверить действующую версию и конфигурацию, сделать защищённую резервную копию D1, проверить режим/epoch и отсутствие второго отправителя. Не запускать seed, не импортировать historical markets как живые позиции. Локальный отправитель ранее отключён при переходе в облако; на другом ноутбуке проверять автозапуск отдельно.

Пример wrangler.example.json предназначен только для явной настройки разработки. Не запускать его как готовую production-конфигурацию. Полный проверенный сценарий начального развёртывания с безопасной синхронизацией живого состояния здесь не предоставлен.
