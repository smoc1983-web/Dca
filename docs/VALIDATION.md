## Телеметрия и журнал очереди на изолированной D1
`operational-telemetry-schema.sql` добавляет отдельные dev-таблицы. `SourceMetrics` хранит время и категорию ответа по известному источнику и операции, включая 429, 451, 5xx, таймаут, отмену и разрыв свечей. В записи отсутствуют URL, тела и тексты исключений. Окно отчёта ограничено семью днями. Это ограничение запроса, политика хранения на рабочем стенде ещё открыта.
`DeliveryAudit` измеряет возраст статуса с момента перехода. Взятие в работу проверяет ревизию и время нового допуска. Из `uncertain` возможны только синтетические решения ручной сверки с явным подтверждением, доставка повторно автоматически не запускается. `HealthNotices` один раз записывает сбой и восстановление с явным интервалом между отметками. Отметка означает право показать результат в тестовой диагностике. Фактическая отправка, очередь доставки этих отметок и подключение к Worker отсутствуют. Miniflare проверяет конкурентные обращения к этому журналу и неизменность live-таблицы alerts.

## Сквозная проверка scheduled Worker
`scripts/check-development-worker.mjs` запускает штатный обработчик `scheduled` с временной Miniflare D1, фиксированным временем и заменой fetch. Любой запрос вне имитаций Binance и Telegram завершает проверку ошибкой. Триггеры из `tests/fixtures/worker-observation.sql` наблюдают переходы в той же транзакции и используются только на стенде. Они не являются миграцией рабочей БД.

Проверяются запрет смены источника при 451, допустимый резервный источник при 503, блокировка продвижения курсора при пропуске истории и восстановление двух DCA. При таймауте после имитации отправки результат остаётся uncertain. При ошибке записи подтверждения он остаётся sending. Следующий такт в обоих случаях пропускает запись и диагностика требует сверки. Две конкурентные задачи воспроизводят гонку 429: второй обработчик читает кандидата до первого ответа и захватывает его после. Проверка срока `next_try` в SQL захвата блокирует преждевременный повтор до истечения паузы. Перегрузка очереди проверяется тремя готовыми записями, по два сообщения на такт. Стенд также записывает единичное восстановление после ручной сверки тестового сообщения. Исполнение происходит в Node.js с локальной привязкой D1.

## HTTP-диагностика тестового Worker
`cloudflare/development-diagnostics.mjs` — отдельная точка входа для локального стенда. Для запуска нужны явный `DEV_WORKER_MODE=synthetic`, временная `DEV_DB` и привязка `DEV_MOCK_NETWORK` к имитации. Плановый обработчик использует штатный tick, но отправляет запросы только через эту привязку и сохраняет сводные метрики источников. В тесте используется отдельный токен авторизации диагностики в заголовке Bearer. Для конфигурации внешнего стенда нужен случайный 32-байтовый ключ в base64url без заполнения. Параметры URL и методы кроме GET отклоняются. При недоступности основного снимка API отвечает HTTP 503. Запрос отчёта не меняет БД и не вызывает внешние сервисы.

`scripts/check-development-diagnostics.mjs` запускает обработчик в workerd через Miniflare 4.20260730.0. Совместимость тестового runtime зафиксирована датой 30.07.2026. Тест проверяет доступ после таймаута Telegram, отсутствие повторной отправки, изменение отчёта после имитации ручной сверки и отказ работы с отсутствующей таблицей. Маршрут запуска такта существует только в файле фикстуры. Никакой конфигурации деплоя не добавлено.

## Воспроизводимый стенд мониторинга
`scripts/check-monitoring-stand.mjs` поднимает два Worker на loopback через Miniflare 4.20260730.0. Основному передаются временная D1 с сохранением на диск и сервисная привязка к отдельному Worker с имитацией Binance/Telegram. Проверка вызывает штатный scheduled-обработчик через локальную RPC-привязку Miniflare, а диагностику читает HTTP-запросом к основному Worker. HTTP-маршрут запуска такта недоступен. Внешние сетевые запросы запрещены. Для каждого запуска создаётся случайный Bearer-токен. После завершения база и токен не сохраняются.

`DEV_MONITORING_POLICY` принимает только известные ключи и целые пороги в миллисекундах. По умолчанию для синтетического режима допустимый возраст последнего такта составляет 2 минуты после конца записанной минуты, запас времени для свечи и возраст очереди составляют 1 минуту, окно источников составляет 24 часа, интервал между отметками составляет 1 минуту. Суточная сводка по умолчанию выключена. При недопустимых значениях отчёт отвечает 503, а такт завершается до чтения БД. Эти значения относятся к тестовому профилю. Стенд ускоряет проверку с интервалом отметки 250 мс и использует окно источников 5 минут. Эксплуатационные пороги перед отдельным согласованием не применяются.

Автоматическая проверка фиксирует инцидент, полностью перезапускает workerd с той же временной D1 и проверяет сохранность очереди, агрегатов и отметки. Старый токен отклоняется. Исход с неизвестным подтверждением не повторяется. После ручной сверки синтетической записи создаётся ровно одна отметка восстановления.

```sh
dca_stand_deps=$(mktemp -d)
npm install --prefix "$dca_stand_deps" --no-audit --no-fund --save-exact miniflare@4.20260730.0
NODE_PATH="$dca_stand_deps/node_modules" node scripts/check-monitoring-stand.mjs
```

## Репетиция добавления журналов к существующей D1
`scripts/check-development-ledger-migration.mjs` сначала создаёт прежнюю схему с синтетическим активным циклом, отметками обработки и четырьмя статусами очереди. Затем перезапускает workerd, добавляет схемы журнала сделок, модельных шагов, бюджета и остатка одной транзакцией и сравнивает все прежние таблицы строка в строку. Намеренно добавленная ошибочная запись в конце пакета проверяет откат всей схемы. Повторный запуск схем идемпотентен.

На добавленных таблицах отдельно проверяются откат курсора, исполнения и тестовой очереди при отказе триггера, атомарная запись ручного исполнения, исправление и повторная сверка денежного остатка. После перезапуска сверяются все новые снимки, позиции, суммы, ревизии и тестовое исходящее событие. Повтор исправления и свечи оставляет одну историю. D1 учитывает строки, изменённые триггерами, в `meta.changes`. Для одного условного INSERT положительный счётчик означает успешную запись, ноль оставляет прежнюю ветку повторной проверки ревизии.

Проверка использует временную локальную D1 и прежнюю схему из репозитория. Модельные позиции не превращаются в подтверждённые исполнения. Проверка не включает импорт живых позиций, согласование начальной сверки для них, авторизацию и облачную D1.
